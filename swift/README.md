# EnsomiRuntime (Swift package)

Swift bindings of the runtime core, generated by UniFFI from `crates/ffi`. Library product `EnsomiRuntime`,
macOS 14 and iOS 17. The manifest is [`Package.swift`](../Package.swift) at the repository root, where SwiftPM
looks for it. An app pins a release:

```swift
.package(url: "https://github.com/ensomi-labs/runtime", from: "0.3.2")
// target dependency: .product(name: "EnsomiRuntime", package: "runtime")
```

A release's binary target is `EnsomiRuntimeFFI.xcframework.zip` on its GitHub release, by URL and checksum
([`RELEASING.md`](../RELEASING.md)). For local development, build the xcframework and point the manifest at it:

```sh
scripts/build-apple.sh        # macOS arm64, iOS arm64, iOS simulator arm64; also regenerates
                              # Sources/EnsomiRuntime/ensomi_runtime_ffi.swift (checked in)
ENSOMI_RUNTIME_XCFRAMEWORK=build/apple/EnsomiRuntimeFFI.xcframework swift test
```

An app built against this checkout depends on `.package(path: "../ensomi-runtime")` and builds with the same
variable set. `swift test` runs every fixture of [`conformance/gameplay`](../conformance/gameplay) through
`GameplaySession`, and its `.osu` files through `parseOsu(text:)`.

## Where the app's types went

| App (EnsomiCore) | Here |
| --- | --- |
| `Mania4KJudgementEngine` | `GameplaySession`: `input(input:)`, `advance(watermarkMs:)`, `score()`, `laneStates()`, `visibleObjects(lowerMs:upperMs:)`, `isResolved()`, `lateInputs()` |
| `Mania4KJudgementEngine.ingest`, `validateEndOfStream` | `GameplaySession.streaming(ruleset:)`, then `appendTokens(tokens:coverageMs:endOfStream:)` (or `append(objects:...)` for protocol pages); `decidedThroughMs()`, `coverageMs()` |
| `Mania4KHitObject` | `ChartToken` (`lane`, `timeMs`, `kind`: `TokenKind`) |
| `OsuMania4KBeatmapStream.parseBeatmap` | `parseOsu(text:)` returning `OsuBeatmap` (`chart`, `title`, `artist`), throwing `OsuError`; the caller reads the file |
| `Mania4KGameplayFeedbackState` | `GameplayFeedback` (a class) |
| `Mania4KNoteRenderLayout.geometry` / `yPosition` | `noteGeometry(object:renderTimeMs:scrollTimeMs:receptorY:)` / `noteYPosition(...)` |
| `Mania4KJudgementEvent` | `JudgementEvent`: `object`, `part`, `tier`, `offsetMs` (= `hitErrorMs`), `timeMs` (= `chartTimeMs`), `objectTimeMs`; `judgement` in `Conveniences.swift` |
| `Mania4KScoreState` | `Score`: `tierCounts`, `accuracy`, `combo`, `maxCombo`, `suggestedAudioOffsetMs`; `perfectCount`, `goodCount`, `missCount`, `judgedObjectCount` on `TierCounts` |
| `Mania4KMalodyTier`, `Mania4KJudgeDifficulty` | `Tier`, `Judge` |
| `Mania4KLaneState`, `Mania4KVisibleObject` | `LaneState`, `VisibleObject` (`id` and `holdingObject` are object indexes) |
| `Mania4KChartValidationError` | `ChartError` (a chart or page) and `OsuError` (a file) |

`GameplaySession.init` throws `ChartError` for a chart the protocol forbids, and `append` for a page. Times are
milliseconds as `Double`; the caller applies the audio offset once and passes chart time. A streamed session
judges only as far as the coverage; `decidedThroughMs()` below the last watermark means the stream fell behind.
Rules, streams and the differences from the Swift engine are in [`crates/gameplay/README.md`](../crates/gameplay/README.md).

## Chart generator

`ChartGenerator` runs the released R2 generator on the device: ONNX Runtime is linked into the xcframework and
runs the graphs, so a chart is one call.

```swift
let generator = try ChartGenerator.open(
    modelDirectory: onnx.path,                     // sed-i/ensomi-r2 onnx/: ensomi-package.json and the files it lists
    options: GeneratorOptions(provider: .cpu)
)
let capabilities = generator.capabilities()        // EnsomiProtocol ModelCapabilities
let result = try await generator.generate(
    pcm: samples, sampleRate: 44_100,               // mono Float PCM at its own rate
    request: GenerateChartRequest(star: 3.5, seed: 7, title: "Song", artist: "Artist", audioName: "song.mp3")
) { phase in print(phase) }                         // .loading, .timing, .rows, .arrangement, .export
try GameplaySession(chart: result.chart, ruleset: Ruleset(judge: .c))
result.osu                                          // the chart as an osu!mania beatmap
result.receipt                                      // EnsomiProtocol GenerationReceipt
```

- The model package's manifest is `ensomi-package.json` ([`docs/model-package.md`](../docs/model-package.md)).
  `checkPackage(manifestJson:)` checks one and returns its `PackageInfo`: `model`, `license`, `notices`, `files`
  (`path`, `size`, `sha256`), `totalBytes` and `config`; it throws `GeneratorError.Model` for a format other than
  `ensomi-package/1`, a `min_runtime` above this runtime's version, another model or pipeline than Ensomi R2 `r2-1.0`
  on `r2` version 1, a path outside the package or out of order, or notices or a config not among the files. A
  downloader fetches the manifest, checks it, then fetches exactly `files` and checks each one's size and SHA-256.
- `open` with an `ensomi-package.json` in the directory checks it, refuses the directory unless every listed file is
  there at its listed size (it computes no hashes), reads the runtime config it names and refuses a manifest that
  leaves out a file that config names ("`<path>` is named by runtime.json but not listed in ensomi-package.json");
  `capabilities().files` are then the manifest's files with their checksums and sizes. Without the manifest, `open`
  reads `runtime.json` and the files it names, as 0.2 did.
- PCM at a rate other than 22050 Hz is resampled with the runtime's soxr tables, `resample-<rate>.json`,
  `.bin` and `-boundary.bin` for 11025, 16000, 24000, 32000, 44100, 48000, 88200, 96000 and 192000 Hz
  (14 MB). The package carries them ([`assets/resampler`](../assets/resampler)) as a resource, which `open` reads
  unless `resamplerDirectory` names another directory; an app bundles nothing for them.
- `lowMemory` releases ONNX Runtime's working memory after each graph run: peak footprint 1.3 to 1.6 GiB
  instead of 2.0 to 2.3 GiB, same charts (measured with every graph on one thread). `nil` turns it on for iOS and off
  on macOS.
- For a directory without the manifest, `modelFiles(runtimeConfig:)` lists the files it needs besides
  `runtime.json`, with the licence notices, and `noticeFiles(runtimeConfig:)` lists those notices, BeatThis's MIT
  licence (`BeatThis-LICENSE.txt`), for the app to show with the model. `open` does not read them, so a directory
  installed without them still opens.
- `exportOsz(osu:audio:receiptJson:)` makes the chart's `.osz` from `result.osu`, the song file's bytes and
  `result.receipt.receiptJson` (`crates/osz`): `generated.osu`, the audio under the name the `.osu` gives it
  (`audio.<extension>`) and `receipt.json`, the layout of the web runtime's `.osz`. The app reads the song and saves
  the archive.
- R2 arranges the song once. The published Python R2 (`r2-1.0`) arranged it a second time when the first
  arrangement missed the star's difficulty target by more than the difficulty fit's seed spread, so its chart
  differs wherever it did; the receipt's `controls.difficulty` records the miss.
- The same model, PCM, request and seed give the same chart on one device with the same options; charts from two
  devices are not claimed equal ([Execution provider](#execution-provider)). `generate(pcm:sampleRate:request:progress:)`
  runs on a thread of its own; cancelling its task stops it at the next graph run or phase with
  `GeneratorError.Cancelled`. Refusals carry EnsomiProtocol's error code in `GeneratorError.Generation`; so
  does a panic in the core (`generation_failed`, "internal error: ..."), after which the generator still works.
  The blocking `generate(pcm:sampleRate:request:listener:cancellation:)` underneath passes the `[Float]` as
  UniFFI's `sequence<float>`; the core keeps one copy until it has made its two frontend streams.
- No call aborts the app on a panic in the core: the gameplay methods that do not throw return an empty or
  default value instead, which the core's tests show it never needs (`crates/gameplay/tests/no_panic.rs`).

### Stored audio stages and play while generating

`prepare(pcm:sampleRate:)` runs the stages that read only the audio (PCM preparation, the spectrogram, BeatThis,
the features and the beat grid), which take most of a generation; any request and seed generate from its result.
Start it when the song is chosen. `Prepared.bytes()` is the runtime's stored form (safetensors layout, valid for this
runtime version and model) for a cache keyed by the audio file's hash; `Prepared(bytes:)` reads it back and throws
`GeneratorError.Model` for bytes it cannot use.

`ChartScheduler` generates for play, from PCM (`fromPcm`) or a `Prepared` (`fromPrepared`), and appends the chart
to a `GameplaySession` page by page inside Rust:

```swift
let lead = LeadPolicy(ruleset: Ruleset(judge: .c), renderLeadMs: scrollTimeMs, marginMs: 0)
let scheduler = try ChartScheduler.fromPrepared(
    generator: generator, prepared: prepared, request: request, mode: .aheadOfPlay, lead: lead
)
let session = GameplaySession.streaming(ruleset: Ruleset(judge: .c))
scheduler.start(atMs: 0, session: session)
if case .ready(let joinMs) = try await scheduler.work() { /* start audio at 0; judging from joinMs */ }
Task { _ = try await scheduler.work() }             // keeps generating ahead of play, then returns .done
// each frame: scheduler.heard(chartMs: heard, wallMs: now); session.advance(watermarkMs: heard)
scheduler.result()                                  // the whole chart, .osu and receipt once done
```

- `.aheadOfPlay` commits a page after each head row of R2's arrangement; `.wholeChart` commits the chart in one page
  at the end. Both make the same chart.
- `.ready(joinMs:)` comes once play from there stays behind the chart to the end:
  c₀ − t₀ ≥ L + max(0, (E − c₀)(p/r − 1)), with the chart committed through c₀, the lead L = max(the ruleset's settle
  lead, `renderLeadMs`) + `marginMs`, the song's end E, the playback rate p from `heard` and the generation's
  throughput r measured as it runs (`rate()`). A slower device starts later instead of stalling.
- `start(atMs:session:)` at a position other than 0 joins at the first time at or after `atMs` + L where no hold is
  open, and leaves the earlier objects out of the session; generation still runs from the song's start. Each start
  takes a new streaming session.
- `work()` runs on a thread of its own, returns at `.ready` and `.done`, and waits while play is far enough ahead. If
  the chart falls behind play (`session.decidedThroughMs()` below the watermark), pause; the next `.ready` says
  where to resume. `stop()`, or cancelling the task, ends it.
- `prepared()` gives the `Prepared` a `fromPcm` scheduler made, to store.
- `request(request:)` changes `star` and `controls` for the chart in progress; the seed, title, artist and audio name
  stay. It is for requests from game events during play (multiplayer attacks, players coordinating), which a pipeline
  that resumes from a committed prefix will apply. R2 takes one until the first page is committed, from `fromPcm` or
  `fromPrepared`, and the chart is then the one a fresh generation with it makes (with `.wholeChart`, which commits at
  the end, a request during the arrangement restarts it); later it throws `GeneratorError.Generation` with
  `unsupported_control` and the generation goes on unchanged.

### Execution provider

Use `.cpu`. Since 0.3.2 it runs BeatThis, most of a generation's time, on the device's performance cores
(`hw.perflevel0.physicalcpu`; elsewhere the available parallelism up to 4) and every other graph on one intra-op and
one inter-op thread. `beatthisThreads` sets BeatThis's count instead: 1 as the parity replays run, 0 to let ONNX
Runtime choose. BeatThis alone over the recorded chunks of two release songs, on a Mac with 4 performance and 6
efficiency cores (Mac17,3, macOS 27.0, runtime 0.3.1 at `ca1053a`, 2026-10-16), in seconds: median and range over
two rounds of five timed passes, one process per arm.

| BeatThis intra-op threads | saigetsu | adventure |
| --- | --- | --- |
| 1, `.cpu` before 0.3.2 | 3.60 (3.02 to 4.40) | 5.30 (4.26 to 6.23) |
| 4, this Mac's performance cores: `.cpu` since 0.3.2 | 2.86 (2.09 to 3.69) | 4.08 (2.92 to 5.36) |
| 0, ONNX Runtime's choice | 2.76 (1.92 to 4.15) | 4.16 (2.94 to 5.32) |

On that Mac BeatThis's outputs were bitwise equal at 1, 2 and 4 threads and at ONNX Runtime's choice, and within
2e-4 of the recording. Other thread counts, core counts and devices are not measured, so a device that runs BeatThis
on another count may give other last bits and, at a near-tie, another chart. Running the chunks concurrently in 2 to
6 one-thread sessions was slower and peaked at 3.5 to 10.7 GiB. ONNX Runtime's choice for every graph (`cpu-threads`
below) made the arrangement 33 to 45% slower, so only BeatThis has more than one thread.

The table and footprints below are from before 0.3.2, every graph on one thread. Measured on an M5 Mac with
`crates/generate-ort/examples/providers.rs`
([`conformance/generate/apple-providers.json`](../conformance/generate/apple-providers.json), runtime 0.2.0, with no
other job on the machine): seconds of the second generation in a process, and the process's peak physical
footprint. When generation starts the footprint is 0.25 to 0.4 GiB: the opened model (0.2 GiB) and the recording
the measurement reads.

| Song | CPU seconds (BeatThis) | Core ML seconds (BeatThis) | CPU peak footprint | Core ML peak footprint |
| --- | --- | --- | --- | --- |
| hesitation-snow | 5.2 (3.7) | 9.2 (7.6) | 1.9 GiB | 11.4 GiB |
| saigetsu | 4.3 (3.0) | 7.6 (6.3) | 1.9 GiB | 11.4 GiB |
| catch-the-moment | 4.2 (3.1) | 7.6 (6.5) | 1.9 GiB | 11.4 GiB |
| adventure | 6.9 (4.2) | 11.6 (8.9) | 2.1 GiB | 11.6 GiB |

`.coreMl` gives BeatThis to Core ML and leaves the other graphs on the CPU. Opening the model then takes 10 s
instead of 0.2 s, BeatThis runs about two times slower and the process needs 11.4 to 11.6 GiB: Core ML takes
BeatThis's dynamic frame axis in 180 partitions. Its charts have the CPU's hit objects on all four songs. Core ML
for every graph fails on the rows graphs' dynamic sequence length. No compute unit or model format helped
(exploratory, hesitation-snow).

Most of the CPU footprint is BeatThis's working memory, which ONNX Runtime keeps after the first run: the
footprint grows by 1.6 GiB during the timing phase on every song. The `providers` configuration `cpu-lean`
(no CPU arena and no memory patterns), `lowMemory` here, brings the peak to 1.25 to 1.45 GiB with the same
charts and times within 0.2 s of `.cpu`. `cpu-threads`, ONNX Runtime's thread count for every graph, took the four
songs from 4.2 to 6.9 s down to 3.4 to 6.0 s with the same charts, though the arrangement took 33 to 45% longer;
`cpu-beatthis-threads` is `.cpu` since 0.3.2.

### Size

The xcframework grows from 8 MiB to 128 MiB (43 MiB a slice). In the app (Release, unsigned), EnsomiCore grows by
31.8 MiB on macOS and 31.5 MiB on iOS, or 21.6 and 21.4 MiB once stripped as an archive strips it. ONNX
Runtime's licence (MIT) and third-party notices are in [`licenses/onnxruntime`](../licenses/onnxruntime); an app that
ships the generator shows them with its acknowledgements. The package carries them as resources:
`ChartGenerator.onnxRuntimeLicenseFiles` gives the URLs of `LICENSE` and `ThirdPartyNotices.txt` to read. They are
also copied to `build/apple/licenses` beside the xcframework.
